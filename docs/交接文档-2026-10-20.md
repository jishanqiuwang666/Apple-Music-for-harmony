## 0.5 2026-10-30~31 会话成果（新会话必读）

这一轮把播放页/歌词页打磨到用户验收通过。**以下都是已验证的结论，不要重新试错。**

### 0.5.1 逐字高亮（最终实现，勿回退）

- **边界只用一个标量**：`xVp` = 从行首开始、**跨视觉行连续累加**的字宽前缀和（换行不归零）；`fillPx = 当前字.xVp + 已唱比例×字宽`。
  `fillWidthStep` 只比较 `xVp` 与 `fillPx`（±带宽半值），**判据里绝不能掺视觉行号**（否则折行句会让第二行的字提前亮）。
- **层数结构恒定**：每个 token 固定 30 层（`EDGE_STEPS` 0..29），宽度 0~w 连续变化。任何“按条件增删层/宽度突变”的压缩优化都会造成闪烁。
- **渐变带**：`EDGE_BAND_VP = 13`，透明序列 `a_j = 1/j`（叠加合成后才是线性坡道）。
- **宽度量化**：`fillWidthStep` 返回值 `Math.round(w*2)/2`（0.5vp），`fillPx` 更新阈值 0.3vp —— 这是「字母局部闪一下」的根治手段（减少每帧重裁）。
- **白层与灰层必须同构**：同字号/同字距/同 `width`（给定宽度，防止折行）。

### 0.5.2 descender（g/j/p/q/y 的下伸笔画）—— 关键坑，别再走弯路

`Text.textOverflow(Clip)` 的裁剪**按段落行边界**执行，`lineHeight` 只影响组件高度、**不改段落内部行高**（官方规格 `arkui-specs/Feat-03-overflow-truncation-spec.md` AC-3.5）。
⇒ **加高 lineHeight / 扩大容器高度都无效**，descender 仍在行边界外被裁。

**正解（三件事必须同时具备）**：
1. 白层 Text **给定宽度**（`width(t.widthVp)`，宽度定死就不会自动折行）；
2. 白层 Text **不要设 `maxLines` / `textOverflow`**（文字自身不裁）；
3. 揭示完全交给外层容器的 `clip(true)`（容器高度已覆盖到行框之外）。

> 曾经只做第 2 步而没给宽度 → 白字自己折成几行，问题更大；曾用 `margin` 负值 / `position` 试图扩大盒子 → 文字被推移成重影。**全程不要用 margin/position 移动文字**。

### 0.5.3 行高与滚动定位

- **行高不写死**：行块不设 `.height()`，由内容自适应（写死高度会让“估算高度≠内容高度”暴露成“有的两句贴近、有的离远”）。
- **定位用实测**：行块 `onAreaChange` 回填 `LineVisual.measuredH`，父组件 `recomputeMetrics()` 用「实测优先 / 估算兜底」重算 `lineCenters/tops/contentHeightVp`，同一帧多次上报用 `setTimeout(0)` 合并；高度变化后把锚点行重新对齐（拖动浏览时不抢）。
- `heightVp` 只是估算，仅用于定位，不参与渲染。
- 段落间距 `PARA_GAP_VP = 32`（Apple 标准，2.15×字高）；字形行框 `GLYPH_BOX_VP = LINE_HEIGHT_VP + 14`，四处文字层（灰字/辉光/白字/活跃层灰字）**统一使用**。

### 0.5.4 译文与 AI 翻译

- **Apple 不给英文歌中文翻译**：实测 8 首英/韩文歌 TTML 的 `<translation>` 与 `<text for=>` 全为 0，`extend=ttmlLocalizations` 也拿不到。
- **中文歌的“译文”是重复文本**：Apple 的 `zh-Hans` 层在正文已简体时不会被简体替换逻辑吃掉，会当成译文行显示。判定**不能信 `<tt xml:lang>`（Apple 常写成 `en`）**，要按正文实际字符：`looksChinese()`（汉字>30% 且无假名/谚文）→ 丢弃译文、且不跑 AI 翻译。
- **AI 翻译通道**：`common/musicbasic/src/main/ets/apple/AiLyricsTranslator.ets`（DeepSeek `chat/completions` + `response_format=json_object`）。
  - 整首一次请求（>80 行分块），**返回数组长度必须与输入严格相等，不等就整体作废**；
  - 按曲目 id 做内存缓存 + single-flight（**不落盘**，用户明确要求）；
  - 凭据在 `AiTransConfig`（Preferences `musichome_ai` / `translate_api_key`，内置出厂 key 兜底），设置抽屉「AI 翻译」一栏可改。
- **译文样式**：字号 `0.68×正文`（≈23.8fp）、最多 2 行、行高 34、上下各 3vp；**全文可见**（`transAlphaOf` 恒返回 1，远近交给行级 `fade`）；颜色用 `colorOf(LYRIC_DIM_ALPHA)`（与未播放正文同亮度）。
- **按钮三态**：无翻译=暗、点一下跑 AI（先置 3 显示进行中）、官方/AI 就绪=亮。用**递增请求号**（`aiRequest++`）而不是布尔值（布尔第二次点击无变化，`@Monitor` 不触发）。

### 0.5.5 播放页交互修复

- **底部按钮误按**：`lyricsEntry`（词/循环）与 `lyricTransport`（上一首/播放/下一首）原本同位置叠放、靠 opacity 互斥 —— **opacity 为 0 的节点仍参与命中测试**，导致点“词/循环”触发切歌。改为按 `lyrics > 0.5` **只挂载一组**。
- **返回分层**：`Index.handleSystemBack()` —— 歌词页 → 先回封面页（`backRequest++` 交给播放页自己收回）；封面页 → `closeFullPlayer()`。
- **系统侧滑返回在播放页不可用是设计使然**：`PhonePlaybackPage.aboutToAppear` 主动 `setGestureBackEnabled(false)`，因为 targetSdk 26 下系统侧滑只会把 App 置后台、不回调 `onBackPressed`（真机日志确认）。播放页是**覆盖层**（不在 NavPathStack），拿不到系统手势；如需真·系统侧滑，唯一路径是把播放页改成 `NavDestination`（代价：现有“从播放条生长”的自定义转场会被系统转场取代）。当前用左边缘 36vp 内起手右滑 + 跟手退进度替代。

### 0.5.7 播放页封面与播放条封面的「交接」（2026-10-31 追加）

**用户诉求**：拉起播放页时，播放条那颗封面**不能待在原地**（原来页内封面从它那里长出去，它自己不动，屏上同时有两颗）；收起时页内封面落回原位，又和播放条那颗叠在一起。要的是「像打开软件一样，播放条那颗封面跟着页面一起长出来，原位变空；收起时落回那个空位」。

**做法（4 个文件，只在首尾各翻一次布尔，不动任何动画曲线）**：

| 位置 | 改动 |
|---|---|
| `features/player/src/main/ets/model/PlayerSheetProgress.ets` | 新增 `@Trace barCoverVisible: boolean = true`（与 `value` 同一个 @ObservedV2 容器；布尔而不是数值，避免播放条每帧重建） |
| `PhonePlaybackPage.onSheetProgressChanged`（既有 `@Monitor('sheet.value')`） | 每帧按进度写它：`atRest = p <= BAR_COVER_REST_EPS(0.002)`，变了才写 + 一条低频日志 `bar cover handoff: visible=…` |
| `PhonePlaybackPage.aboutToDisappear` | 兜底置回 `true`（页面不在了，播放条必须有封面） |
| `view/Player.ets`（HDS miniBar 里的播放条） | 新增 `@Param sheet`；**只给「封面图 + 播放/暂停字形」加 `opacity(flag?1:0)`** |

**三个关键判断（改前先读，别推翻）**：

1. **用 opacity 不用 visibility**：`opacity(0)` 仍参与命中 —— 「在封面上上滑呼出播放页」的手势正挂在那个 Stack 上，`visibility` 会在拖到一半把节点从命中树里摘掉。
2. **进度环（`MiniBarProgressRing`）必须留在原位、不跟着藏**：它 58vp 比封面 48vp 大一圈，落回来的封面只盖住内侧 5vp 外的环永远露着。若连环一起藏，落地那一帧环会「啪」地冒出来 —— 这正是 0.5 之前修过的「环和文字过一瞬间才出现」。
3. **换手阈值取 0.002（≈1vp 行程）**：这一档两枚封面的圆心差 ~1vp、边长差 ~0.5vp，完全重合所以看不出接缝；取 0.02 就会看到播放条那颗先露出来又被盖住（= 用户反馈的「两颗叠在一起」）。

回滚：`backups/musichome-cover-handoff-20261031-022006.tar.gz`（含改前的 5 个文件）。

### 0.5.8 落点「偏左下一点点」的定量修法（2026-10-31 同轮追加）

用户反馈：收起时页内封面落回播放条，**比原位上那颗偏左、偏下一点点**（历史遗留）。这次不再靠截图估，改用 `uitest dumpLayout` 直接读真机布局（App 停在主页即可，只读）：

| 节点 | px bounds | vp |
|---|---|---|
| miniBar 60vp 方槽 | `[1013,2414][1208,2609]` | `x 311.69..371.69, y 742.77..802.77` |
| 槽里的封面（48vp） | `[1032,2433][1188,2589]` | 圆心 **(341.5385, 772.6154)** |
| 进度环（58vp） | `[1016,2417][1205,2606]` | 圆心 (341.6923, 772.7692) |

反算旧常量的落点误差：`(-0.306, +0.138) vp = (-1.0, +0.4) px` —— 与用户描述的「偏左下」完全对上。三处数值改法（`products/default/src/main/ets/pages/Index.ets`）：

| 常量 | 旧 | 新 | 依据 |
|---|---|---|---|
| `BAR_RIGHT_MARGIN_VP` | 17 | **16** | (1260−1208)/3.25 |
| `BAR_BOTTOM_MARGIN_VP` | 34.17 | **34.1538** | (2720−2609)/3.25 |
| 封面圆心偏移 | x=30.54（y 用「槽高一半 30」） | **x=y=29.8462** | 封面 px `1032..1188` 相对槽左上角 |

为什么偏移不是 30：槽里 `Row(padding 1/4)` + 58vp 进度环，内容盒只有 55 < 58 → ArkUI **靠左排**（老坑），环占 `槽左+1..+59`，封面在环里居中后光栅化到 `1032..1188`，圆心就是 `槽左+29.8462`。**取封面圆心而不是环心**（眼睛比对的是两颗封面）。

另修两处「二阶误差」：

1. **封面几何的进度只钳下界**（`PhonePlaybackPage.coverP()`）：收起到底时弹簧会略冲过 0，原来会用负进度把封面外推到播放条下方 → 落地前一两帧看见封面沉一下。上界（展开时的过冲回弹）保持不变。
2. **换手阈值 0.002 → 0.0005**：换手时页内封面离落点还有 `p × ~480vp` 的距离，0.002 是近 1vp（≈3px）的残差 —— 会和常量误差混淆。

改完落点与播放条封面**逐像素重合**（页内封面正好光栅化到 `1032..1188 / 2433..2589`）。若以后 HDS bar 尺寸变了，**只能用 dumpLayout 复量这三个数**，不要再用截图圆拟合。

### 0.5.9 艺人板块三件事（2026-10-31 同轮）

**① 收藏横排满宽**
`ArtistsPage` 里横排 `List` 的 `.padding({left:16,right:16})` → `0`，同时 `favPadX` 16 → 0（拖动落点换算用它）。dumpLayout 实测：首个卡位 x=0，最后一个卡位被屏幕右缘裁掉（0..387.69），满宽生效。

**② 拖动排序不跟手 —— 真因是「单位换算错了 3.25 倍」**

`TouchObject.windowX / windowY` **本来就是 vp**（SDK `common.d.ts` 里逐个字段写着 `Unit: vp`；API 10 起由 px 改成 vp），而代码里又做了一次 `this.getUIContext().px2vp(...)`。于是**手指走 100vp，卡片只走 31vp** —— 永远追不上手指，用户感受就是「极其不跟手」。
修法：`onFavHoldStart` / `onFavHoldMove` 三处去掉 `px2vp`，参数名 `wxPx` → `wxVp`，注释写死「单位 vp，别再补回换算」。

> 同一类错误在本项目还有 5 处（当前**刻意未动**，只影响「甩多快才触发」不影响跟手）：
> `Player.ets:491`、`PhonePlaybackPage.ets:2274/2303`（甩动阈值被抬高 3.25 倍）、`Index.ets:759/777`（抽屉跟手只有 31%、关闭速度阈值抬高 3.25 倍）。
> `GestureEvent.offsetX/offsetY` 单位是 vp、`velocityX/velocityY` 是 vp/s（`gesture.d.ts` 明确），要改时一起改。

**②-b 顺带做过的性能优化（保留）**
跟手位移原来是 `ArtistsPage` 的 `@Local favFloatDx/Dy`，指针每动一次整页（垂直 List + LazyForEach 160 位艺人 + 收藏横排）diff 一遍，帧率必然掉。
改为：`@ObservedV2 class FavDragOffset{@Trace dx/dy}` + 独立组件 `FavoriteFloatCard`（外层只挂 translate、内层才是卡片本体与 1.08 缩放，与改造前的两层结构一致）。现在每帧只重建那一张小卡片。
命名坑：`@Param` **不能叫 `offset`**（与组件通用属性 `offset` 冲突，编译报 10505001），所以叫 `dragOffset`。

**③ 拖动顺序重启后回退**
`persistFavOrder` 只写了数据库 `favorite_artists.sort_order`，而横排里还有一批是从 **Apple Music ⭐** 并进来的艺人 —— 它们在 `favorite_artists` 表里**没有行**，`UPDATE sort_order` 打空，重启后 `refreshFavorites` 只能按 Apple 给的顺序排。
修复：另存一份**全量顺序**到 Preferences（`musichome_fav` / `fav_artist_order_v1`），`refreshFavorites` 末尾用 `applySavedOrder()` 重排（不认识的新收藏排在后面）。数据库写入保留。

**④ 艺人作品每次都重新联网 + 加加载动画**
新增 `features/library/src/main/ets/util/ArtistWorksCache.ets`（进程内缓存）：`loadWorks()` 先查缓存 → 命中就**零请求**直接渲染（也不显示加载动画）；未命中才走 `fetchWorks()`（原逻辑原样搬过去），成功写缓存、失败不写。`applyWorks()` 用 `slice()` 产生新数组，保证「是否已在库」的标记会随重绘更新。
`fillAllWorks()`（收藏艺人进页面自动补齐全部作品 + 整库同步，非常重）加 `FILL_THROTTLE_MS = 6h` 节流：同一次运行内每位艺人只跑一次。
首次进入有 `LoadingProgress + 正在加载作品…`（挂在作品提示下方）。
四个入口（收藏横排 / 艺人列表 / 搜索结果 / 搜索浮层）都 push 同一个 `ArtistDetail`，所以在这一层做缓存即全覆盖。

2. 同样的 `00308018 Unknown Error` 但日志里 SignHap 正常、最后是 `Server has disconnected`
   → hvigor daemon 挂了：`pkill -9 -f hvigor; rm -rf ~/.hvigor/daemon` 后重跑（偶发，重跑一次也能过）。

### 5.2 已查实的机制（**别再重复调研**）

1. **微信链接卡片的封面只由目标页的 `og:image` 决定**，由微信服务器自己抓。App 传给系统分享面板的 `thumbnail` 只影响**系统面板的预览**，与微信里的卡片无关 —— 这就是「面板有封面、微信没有」的根因。
2. Apple Music 页面本身 og 齐全（`og:image` 为 1200×630，mzstatic 允许无 referer 直取，UA 无关）。三种 UA 实测同一份页面 ⇒ **苹果侧没问题，是微信那一侧不采用**。
3. 设备实测 `bm dump -n com.tencent.wechat`：微信注册给系统分享面板的入口只有
   - `general.image`（scheme `file`，maxFileSupported 9）
   - `general.hyperlink`（scheme `https`，1）
   - `general.plain-text`（scheme `content`，1）
   另外还有 `wxopensdk://open_sdk_request_link` / `open_sdk_get_a8_key` 等 **SDK 通道**（说明 B站/Apple Music 走的就是这条）。
4. 微信官方鸿蒙分享文档（`developers.weixin.qq.com/doc/oplatform/Mobile_App/Share_and_Favorites/ohos.html`）：
   - `WXWebpageObject`（网页）：支持**会话 + 朋友圈**，`WXMediaMessage.thumbData` ≤64K 即我们的封面；
   - `WXImageObject`（图片）：支持**朋友圈**；
   - `WXMusicVideoObject`（音乐卡片，1.0.21 起，2026-09 新增）：需 OpenSDK 签名，最接近 Apple Music 的形态。
5. SDK 接入要求（官方接入指南）：微信按 **AppID + 鸿蒙 `appIdentifier` + Bundle ID 三元组**校验后台登记记录，失败会报「Bundle ID 信息校验不通过」「第三方应用信息校验失败」。`appIdentifier` 由华为签名证书派生 ⇒ **伪造 Apple Music 身份结构上不可能**（也要不到 `com.apple.*` 的签名）。
6. **朋友圈没有系统级入口**：系统分享面板只能发到微信会话；朋友圈必须「微信内打开链接 → 右上角… → 分享到朋友圈」，或用 OpenSDK 的 `WXSceneTimeline` 直发。

## 8. 调试手法与已知坑（省时间用）

**诊断**

- 日志：`hdc shell hilog -r` 清缓冲 → 操作 → `hdc shell hilog -x` 导出后 grep；hilog 缓冲只有几秒，要轮询抓。
- 截图：`hdc shell snapshot_display -f /data/local/tmp/x.jpeg` + `hdc file recv`（后缀必须 `.jpeg`）。
- 布局：`hdc shell uitest dumpLayout ...`，看 `bounds` / `scrollable` / `hitTestBehavior` / `zIndex`。
- **不能**用 `hdc file recv` 读 App 的 `filesDir` / `cacheDir`（660 属主 app uid，`permission denied`）；只能靠日志里的字节数、或屏幕像素量测。

**ArkUI / 鸿蒙 坑（本项目反复踩过）**

- `keyframeAnimateTo({delay})`：每个 keyframe 的闭包在**调用时**就写目标值，逐字形排程会整行瞬间全白。
- 逐字形 `setTimeout + animateTo`：只有第一个字动（其余直接跳到终态）。
- 百分比宽度做裁剪/进度：`width('30%')` 按父级约束解析 → 容器被撑开，Flex 每项独占一行（真机表现为「一个字一行」）；必须 `MeasureUtils.measureText` 量出 vp 再用数值。
- `ForEach` key 不变 → 子项持有旧 `@Param` 对象，之后的 `@Trace` 写入全部不上屏；key 里要带「结构代数」。
- `radialGradient` 的 `radius` 不能带单位（写 `'200vp'` 会静默失效成一整块半透明矩形）。
- `Image.draggable` 自 API 11 默认 true，会抢长按/拖拽；卡片里的封面必须显式 `false`。
- `Scroll` 会把「比视口短的内容」垂直居中 → 内容列加 `constraintSize({ minHeight: '100%' })`。
- 根节点用 `Column` 叠「全屏背景 + 内容」会把内容挤成 0 高（整页空白）→ 必须 `Stack`。
- 沉浸光感只在「弹窗类 / Navigation 标题栏 / 底部 TabBar」生效，且需 `module.json5` 的 `ohos.arkui.UIMaterial.state = enable`。
- Preferences 值里不能有控制字符（`\u0001` 会让整个 store 下次启动变 `.broken`），复合键用 `JSON.stringify` 或可打印分隔符。

**接口坑（Apple）**

- 资料库 id（`i.`/`l.`/`r.` 前缀）≠ 目录 id；写收藏/查 catalog 必须用目录 id（`?include=catalog` 拿）。
- 收藏写入是最终一致（约 6 秒），UI 必须乐观更新。
- HarmonyOS `@kit.NetworkKit` http **不允许 POST/DELETE 传空 body**，要给 `'{}'`。

**bash 工具坑**

- 命令行里的中文会被吞 → 中文路径/内容一律写进 `.py` 脚本再 `python3` 执行；heredoc 会卡死 shell。
- 不要在后台/并行跑 `devecocli build`，会把 hvigor daemon 卡住。
