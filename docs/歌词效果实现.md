# 歌词效果是怎么做出来的

这是我最满意的部分。它看起来只是「字一个个变白」，但要做到**连续、柔和、不抖**，
ArkUI 里几乎没有一条现成的路。下面按「时间轴 → 视觉 → 滚动 → 性能」四层记录。

代码：`features/player/src/main/ets/view/AppleLyricsView.ets`（视图 + 动画排程）、
`common/musicbasic/.../AppleLyrics*`（TTML 解析）。

---

## 一、时间轴：别用「进度 + 墙钟推算」

最常见的写法是「记住上次进度和时间戳，每帧用墙钟推算当前位置」。**它会累积误差**：

- AVPlayer 的 `timeUpdate` 约 **1 秒**一次；
- 一旦有一拍没跟上（缓冲、解密耗时、seek 之后进度被冻结），插值误差**不会自己收敛**，
  实测能领先真实播放头 **15 秒**；
- 而歌词是**绝对时间轴**（每行时间戳相对整首歌），错 3 秒就落到别的行上——
  歌开头句子间隔只有 2~3 秒，于是表现为「前半段完全不亮、后半程正常」，极具迷惑性。

**正解**：直接读播放器播放头。

```ts
// MediaService
public playheadMs(): number { return this.player?.currentTime ?? -1; }
// 100ms 心跳采样，只有采样值连续不变（属性粒度粗）才用墙钟补齐，且给补齐上限 400ms
```

补齐上限必须**远小于最短条目间隔**（歌词行常 1.5~3s，取 400ms），否则会「虚推跨行」。

## 二、逐字：每个字一份时间窗

Apple 的 TTML 提供词级（甚至音节级）时间。中文按**一字一段**、拉丁按**整词**一段
（字母级会闪，而且节点数暴涨）。词内时间按字数摊开：

```
第 g 个字（共 n 个）：[词开始 + g·d/n, 词开始 + (g+1)·d/n)
```

**排程要用定时器，而不是每帧写值**：
换行那一刻算出该行每个字的时间窗，到点后 `animateTo({duration: 段长, curve: Linear}, () => fill = 1)`。
白字层宽度从 0 长到 1，字与字首尾相接，整词连续推进。
定时器句柄必须存数组，换行 / seek / 页面销毁时全部 `clearTimeout`，否则旧排程会串到新行。

两个已证伪的做法（别再试）：

- **心跳驱动 `animateTo`（时长=剩余）**：汉字时间窗常 150~300ms，100ms 心跳只采到 2~3 个点，
  中间过程画不出来 → 观感「一个字一个字蹦出来」。
- **`keyframeAnimateTo` 三段关键帧**：实测关键帧的闭包在**调用时**就写入目标值，
  于是整行瞬间全白。

填满瞬间给一个轻弹：`1 → 1.055`（110ms）再 `springMotion(0.3, 0.62)` 落回，配合 2vp 上抬。

## 三、柔和边缘：透明度要用叠加公式反解

ArkUI **没有 alpha 渐变遮罩**：`mask()` 只吃几何形状，`clip(true)` 是硬切，`blur()` 会连字一起糊。
所以「白字从左往右长出来」的边缘只能用**多层递进裁剪**逼近：同一段文字叠 N 份白字，
宽度依次递增、透明度依次递减。

关键在于**透明度取什么值**。这些层是叠加覆盖的，某像素的最终白度是

```
1 − Π(1 − a_i)         // 对所有比自己宽的层求积
```

- 按「每层等幅下降」（0.92 / 0.84 / 0.76 …）调：外层叠了很多层，累积后迅速接近纯白 →
  前几 vp 一片死白、后面突然掉下去，屏幕上就是**一条硬线**，怎么调带宽都消不掉。
- 想要 N 层合成出 `1 → 0` 的**线性坡道**，解是 **`a_j = 1/j`**：
  `[1, 1, 1/2, 1/3, 1/4, …, 1/N]`。推导：要求宽度第 k 段处白度 = k/N，即 `Π_{i>k}(1−a_i) = k/N`，
  相邻相除得 `1 − a_{k+1} = k/(k+1)`。

配套参数：带宽 6vp + 16 层 ≈ 每层 1.2px（@3.25x 屏），肉眼连成渐变；带宽还要按字宽收敛
（`min(band, 字宽 × 0.5)`），否则英文单字母会被整块盖住。

**同源的另一个坑**：不要用「抬整字透明度」做预热。抬 alpha 是整字一起亮，填充是边界在推进，
两者同时开，用户看到的是「唱到哪个字，那个字的底就亮一度」——逐字效果被彻底破坏。
预热只能由白层边界自然跨字完成。

## 四、滚动：自己持有位置，别让 List 追

歌词要跟着播放不断平移。用 `List + scrollTo` 会踩一整串坑：

- `currentOffset().yOffset` 在动画进行中是**滞后**的，「按比例追随」这类算法会因此失准；
- 每次 `scrollTo` 都是重新下发一个动画，目标一变就从当前速度重新起步 → 观感「忽快忽慢、在找补」；
- `edgeEffect` / 内容不足 / 补滚会让「目标位置根本到不了」→「有时滚有时不滚」；
- 程序化滚动与用户手势共享同一套 `onScrollStart/Stop`，判断「是不是用户滚的」永远不可靠。

**正解**：`Stack(clip) { Column(全部内容).translateY(-scrollY) }`，用 `@Local scrollY` 自己持有位置，
换行时**一次** `animateTo({ duration: 260~320, curve: springMotion(0.2, 0.9) })` 赋新值。
动画被打断时 ArkUI 会从当前渲染值继续，速度连续；同一时刻只有一个动画，结构上不可能「找补」。
首次定位 / seek 直接赋值（不带动画）。

必须保留两个垫片：顶部 = 锚点位置（歌词区高度的 52%，实测活跃行居中线约屏幕 51%），
底部 = 视口高 − 锚点，否则首末两行到不了目标位。代价是失去 List 的虚拟化
（100~200 行量级没问题，再多要自己做窗口裁剪）。

**滚动触发点还有个隐形坑**：很多歌词把每行的 `endMs` 直接写成「下一行开始时刻」，
于是 `pos >= curEnd` 实际等于「下一句开口那一刻才开始动画」——用户感知是
「一行都唱到一半了才开始往上走」。正解：

```
startAt = min(curEnd, nextStart − 动画时长 − 80ms)
startAt = max(startAt, curEnd − 500ms)   // 防长间奏提前太久把正在唱的行推走
```

## 五、观感：弹簧与景深

- **弹簧**「生硬」几乎总是阻尼太接近 1：`springMotion(response, damping)` 里 damping 0.9 以上
  没有过冲，看起来是「匀速滑到目标然后突然停住」。想要可见回弹取 **0.68~0.75**
  （过冲 3~6%），同时把 response 和 duration 一起拉长（0.40 / 430ms）。
  排查顺序：先看 damping，再看 response，最后才看 duration。
- **景深模糊按需**：逐项 `.blur()` 是最贵的属性（每个都进离屏渲染）。
  只给离焦点 5 项以内加模糊，其余靠 `opacity` 压暗，观感几乎无差、开销降一个数量级。
- 全屏后处理（如 `linearGradientBlur`）在内容移动时**每帧重算**，滚动期间应降到 0，停手 200~300ms 恢复。

## 六、怎么验证（别只靠眼睛）

- 截 8~10 帧，统计「活跃行最亮行的白/灰像素比」，连续填充应呈梯度
  （实测 0.11 → 0.46 → 0.70 → 0.90）。各帧都接近 1.0 = 瞬间填满；接近 0 = 没填。
- 静态截图只能验证**粒度**（把播放头钉在某个词中间，看同一词内是否一半白一半灰）；
  顺滑度只能真机播放看。
- 判断「有没有硬边」：在无文字的条带上扫相邻像素亮度差，台阶 > 8/255 就是有边。

## 七、已知不足

- 停手 4 秒没有「回位」以外的浏览手势（不能上下自由拖）；
- 超长歌词（>200 行）没有做窗口裁剪，节点偏多；
- 逐字时间依赖 TTML 的质量，老歌常常只有行级时间，这时退化成整行渐变。
