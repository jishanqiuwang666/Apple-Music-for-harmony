# 播放历史（继续播放）与切歌卡死 —— 排查与重构记录（2026-10-17）

用户反馈两件事：

1. **播放历史有时不生效**，尤其是**专辑**不生效，歌单正常。
2. 专辑播完第一首之后，**第二首不播**，只有**退出应用重启**才恢复。

---

## 一、播放历史（专辑的「继续播放」）不生效

### 定位：直接查库，别猜

「播放历史」在本项目的实现是 RDB 表 `playback_resume`（专辑 / 歌单各记一份
「上次停下的那首 + 位置」，页面据此显示黄色「继续播放」按钮与曲目黄标）。

把库拉下来用 sqlite3 一看就清楚了：

```bash
HDC=/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/toolchains/hdc
$HDC file recv /data/app/el2/100/database/com.sample.musichome/musichomesample/rdb/music_library.db /tmp/ml.db
cp /tmp/ml.db /tmp/q.db; $HDC file recv .../music_library.db-wal /tmp/ml.db-wal; cp /tmp/ml.db-wal /tmp/q.db-wal
sqlite3 /tmp/q.db "SELECT context_key, kind, song_uri, position_ms FROM playback_resume;"
```

结果只有两行，**全是 `p|` 开头的歌单**，`a|`（专辑）一条都没有 ——
与用户描述完全一致，说明不是「读的时候丢」，而是**压根没写进去**。

### 根因

进度写入链路：

```
MediaService.persistProgress()            // 播放中每 5s / 暂停 / 停止 / 换轨各落一次
  → saveContextProgress(songUri, ms)
    → PlayContextKeys.progressKey(context)  // album → "a|<id>"；playlist → "p|<id>"；其它 → ''（跳过）
      → MusicDbApi.saveResume(...)
```

而队列来源上下文（`playContextKind` / `playContextId`）是**播放入口**写进去的。
对比两个详情页：

| 页面 | 调用 | 上下文 |
|---|---|---|
| 歌单详情 | `playSongList(songs, i, true, playlistContext(...))` | ✅ 有 |
| 专辑详情 | `playSongList(this.songs, i, true)` | ❌ **没传** → 退化成 `libraryContext()` → `progressKey === ''` → 直接 return |

所以专辑从头到尾都没写过一行进度；歌单一直是对的。这也解释了「有时」——
只有从**歌单**、艺人页等入口播同一张专辑时才会碰巧记上（那些入口的 context 不是 album）。

> 注：`PlaybackHelper.playAlbum()` / `playAlbumAt()` 本身是传 context 的，
> 但专辑详情页为了「队列与界面显示一致」（列表可能被去重/可播过滤裁剪）而
> **绕过了这两个封装、直接调 `playSongList`**，改的时候就漏了 context。

### 修复

- `AlbumDetailPage.playAlbumAll()` / `playAt()` 都补上
  `PlayContextKeys.albumContext(this.albumName, this.artistName)`；
- `PlaybackHelper.resumeAlbum(albumName, artist, songs?)` 支持传入页面当前列表，
  续播的队列/索引与 `playAt` 完全一致（目录专辑的临时曲目也能续播）。

**验证**：修复后同样跑一次「播专辑 10 秒」，库里出现
`a|["Debussy: Piano Works","瓦尔特 · 吉泽金"] | album | apple:i.qQdGz4qTNqDg5EA | 70610` ✔

## 二、第一首播完第二首不播（只能重启 App）

### 根因：换轨路径上有三条竞态，全部指向「两条装载链互相踩」

旧实现的换轨是：

```
loadAsset(i+1)
  → await stop()                 // 旧实例 completed → stopped
       └─ stateCall('stopped') 里 this.avPlayer.reset()      ← ① 连锁 reset → idle
            └─ stateCall('idle') 里 await build() + 设 fdSrc  ← ② 与主链抢同一首歌
  → explicitLoad = true
  → await recreatePlayer()       // 建新实例，然后 await old.release()   ← ③ 在旧实例回调栈里 await release
  → await applySongSource()      // 设 fdSrc / prepare
```

三个问题：

① **`stopped` 里 reset() 会连锁触发 idle**，而 idle 分支本身就会
「build 当前曲目 + 设 fdSrc + 起 prepare 轮询」—— 于是同一首歌被装了两遍，
两条链互相清 fdSrc / 互相重置 `isPrepared`。

② **状态标志是「全局」的，不区分实例**：旧实例的 `prepared` 事件会把
`isPrepared` 置 true，新实例的 `waitPrepared()` 第一行就是
`if (this.isPrepared) return;` → **直接返回、永远不给新实例 prepare**
→ `play()` 走到「已 prepared」分支去 `play()` 一个还没装源的播放器 → 静默无效。
重启 App 会重建整套对象，所以「重启就好」。

③ **在旧实例自己的 `stateChange` 回调栈里 `await old.release()`**：真机上
release 要等回调返回，回调又在等 release —— 换轨链直接卡死，`explicitLoad`
再也回不到 false（之后所有 idle 事件都被让路掉）。

### 重构（目标：一条唯一路径 + 实例身份隔离）

`MediaService` 的换轨逻辑重写为：

1. **`switchTrack(song, loadOnly)` 成为唯一换轨入口**
   （`loadAsset` / `loadAssetBySrc` 都只做参数归一 + 校验，然后交给它）：
   - 期间置 `explicitLoad`，让旧实例残留的 idle 事件让路；
   - `loadToken` 递增，**只有最新一次装载生效**（晚到的旧链自动作废、并释放自己建出来的实例）；
   - **先建新实例、成功后再切 `this.avPlayer`、再异步释放旧实例**；
     建实例失败时**保留旧实例**（不会出现「一个播放器都没有」的死状态）；
   - 旧实例**不 stop、不 reset**，直接 `void safeRelease(old)`（不 await）——
     少一次状态迁移就少一类竞态，也避免在旧实例回调里等它自己释放。
2. **事件全部带实例身份守卫**：`bindPlayer(player)` 的每个回调先判
   `this.avPlayer === player`，否则丢弃。旧实例释放途中吐的
   stopped / idle / released 再也不会污染新实例。
3. **`completed` 换轨挪到宏任务**：`setTimeout(() => playNextAuto(false), 0)`，
   绝不在音频回调栈里做「建实例 / 释放实例」。
4. **`stopped` 分支不再 reset**（那个连锁 idle 就是竞态 ① 的源头）。
5. `waitPrepared` 的轮询仍在（应对「prepare 成功但不派发 prepared 事件」的机型行为），
   但配合上面的守卫后不会再拿旧实例状态误判。
6. 顺手清理：
   - `stateCall` 从 `async` 改回**同步**（异步动作全部下发给 switchTrack / applySongSource），
     状态回调里不做长耗时操作，时序才可预测；
   - `idle` 分支不再复制一遍「build + 设 fdSrc + 起轮询」，改为复用 `applySongSource`（少 ~30 行重复代码）；
   - `pendingLoadBySrc`（按源播放、播放器还没建好时的挂起请求）**以前只写不读**，
     冷启动瞬间的按源播放会被静默丢掉 —— 现在 `applyPendingLoadRequest` 会一并消费。

### 真机验证（自动回放整条危险链路）

临时自检（验收后已删除）：播一张 3 首的专辑，依次把每首拖到结尾触发完成事件，
最后再点一次播放：

```
TEMP-PLAY-DEMO [s0] seek -> 312966 (idx=0 dur=315466)
TEMP-PLAY-DEMO [s1] 自动切到下一首 ok: idx=1 dur=216317
TEMP-PLAY-DEMO [s3] 第二首后自动切换 ok: idx=2 dur=217385
TEMP-PLAY-DEMO [s5] 队列播完已停止 ok: idx=2 isPlay=false
TEMP-PLAY-DEMO [s6] 再次调用 play()
TEMP-PLAY-DEMO [s6] play() 之后: idx=2 pos=19806 dur=217385 isPlay=true title=Deux Arabesques …
```

即：**连续两次自动切歌正常、队列播完正常停止、播完之后再点播放能重新播**。
`hilog` 里没有 `createAVPlayer failed` / `idle reload failed` / `Too many playback errors`。

## 三、可复用的经验

1. **功能「没生效」先查数据面**：把 RDB 拉下来 sqlite3 一查就知道是没写还是没读
   （本次 3 分钟定位，比读一小时代码快）。hdc 读库不需要 root。
2. **播放器状态机要按实例隔离**：任何「换实例」的播放器（AVPlayer/ExoPlayer 类），
   事件回调都必须带实例身份守卫，状态标志（prepared/needPlay）也要随实例重置，
   否则旧实例的迟到事件会污染新实例，症状是「偶发、只能重启」。
3. **不要在自己的回调栈里 await release()**：换轨/换实例这类动作一律挪到宏任务里做。
4. **上下文/来源这类「隐式参数」必须由播放入口统一写**：绕过封装直接调底层 API
   （本次专辑页为了列表一致性直接调 playSongList）最容易漏掉上下文，漏了就静默丢功能。
5. 队列播完再播放、连续自动切歌、失败重试——这三条链路一定要做成自动化回放自检，
   否则只能等用户偶发遇到。
