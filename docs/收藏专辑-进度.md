## 十二、播放不通的根因：播放链路是「按歌曲 id」的（2026-09-21，已定位）
- 详情页曲目行的点击 → `this.playAt(index)` → `PlaybackHelper.playAlbumAt(albumName, artist, index)`
  ⇒ 它是**按专辑名+艺人在本地库里查行**再播放 ⇒ 临时/目录专辑库里没有行 ⇒ 静默不播（与日志"点完没有任何播放行"完全吻合）。
- `PlaybackHelper` 有通用入口：`playSongList(songs: SongApiDto[], startIndex, openPlayerUi, context?, startPositionMs?)`
  ⇒ 可直接把内存里的曲目列表交给播放器（专辑/歌单/艺人都是走它的）。
- **但**该入口内部把队列与待播歌曲都落成 **`pendingPlaySongId = songs[i].id`**（数字 id）
  ⇒ 临时曲目不在 `songs` 表里，这个 id 指向不到正确行 ⇒ 直接调用它**仍然播不出正确的曲子**。
- 因此要真正打通"目录专辑直接播放"，二选一：
  **A（推荐）** 扩展播放意图/队列，让它能承载 **`src`/`apple:` 标识**（项目早先的目标里就有"队列改为稳定 apple: URI 持久化"这一条），
  即 intent 增加 `pendingPlaySrc`（或队列项带 uri），播放服务优先用 src 解析；
  **B（快但脏）** 把目录曲目以**隐藏标记**写入 `songs` 表（所有列表查询处过滤该标记，确保不出现于「全部歌曲」），
  播完/离开页面后清理；风险是污染面较大、易被后续查询漏过滤。
- 结论：这一步需要动播放服务/意图（约 1 轮），且**不能破坏**现有本地文件与资料库 Apple 歌曲的播放路径。

## 二十四、推翻二十一节：⭐收藏**能读到**，机制是 `extend=inFavorites`（2026-09-26 上午）

用户质疑「那为何我能看到喜爱的歌曲呢 / 三者的收藏没关系，想想别的办法」⇒ 重新调研，**结论翻案**。

### 真正的机制（真机 + 真账号已验证 ✔）
收藏状态不在 ratings 里，而是**属性扩展**：

```
GET /v1/me/library/albums ?limit=100&offset=N&extend=inFavorites
GET /v1/me/library/artists?limit=100&offset=N&extend=inFavorites
→ data[].attributes.inFavorites : true / false
```

- 不带 `extend` 时，Apple **根本不返回** `inFavorites` 字段（真机对照：`all=0`）；
- 文档依据：Apple 官方 "Add resource to favorites" 页写明「favorite 一首歌 → 进 favorite songs 歌单；
  favorite 专辑/歌单 → 在 library 视图里可按 favorited 过滤」，且属性扩展参数说明就是 `extend`；
- 社区实现佐证：MusadoraKit `InFavoritesParser` = `GET /v1/catalog/{sf}/{type}/{id}?extend=inFavorites`，

## 二十七、专辑详情页「心形」收藏按钮 —— 写进 Apple Music（2026-09-26 下午，用户要求）

用户要求：像艺人页那样在专辑页放一个心形图标，点一下收藏、再点取消，并且
**要真的改 Apple Music 的资料库，不能只改手机端显示**。

### 写入接口实测（真机 · 真账号，用「当前未收藏」的专辑做实验，结束已复原）
按顺序试了所有候选，结论如下：

| 目的 | 调用 | 结果 |
|---|---|---|
| **收藏** | `PUT /v1/me/ratings/albums/{目录id}` body `{"attributes":{"value":1},"type":"ratings"}` | 200 → **约 6 秒后 `inFavorites` 变 true** ✔ |
| **取消** | `DELETE /v1/me/ratings/albums/{目录id}` | 204 → **约 6 秒后变 false** ✔ |
| 读状态 | `GET /v1/me/library/albums/{l.xxx}?include=catalog&extend=inFavorites` | 一次请求同时拿到**目录 id**与 `inFavorites` ✔ |
| （弃用） | `POST /v1/me/favorites?ids[albums]={目录id}` | 202 被接受，但**实测不改 `inFavorites`** ✘ |

要点：
1. **写入必须用目录 id**（不是 `l.xxx`）——资料库 id 只用于读；目录 id 通过 `include=catalog` 取；
2. **propagation 约 6 秒**（真机轮询实测：PUT 后第 6 秒读到 true、DELETE 后第 6 秒读到 false），
   所以 UI 必须**乐观更新**，不能写完立刻回读；
3. 之前 `POST /v1/me/favorites` 那 40008/"Parameter error" 的坑：**HarmonyOS http 不允许 POST/DELETE 传空 body**
   （本地就报 `Parameter error`，根本不是 Apple 拒绝），必须传 `'{}'`。

### 实现
- `AppleApi` 新增：
  - `getLibraryAlbumFavState(libId)` → `AlbumFavState{catalogId, inFavorites}`；
  - `getCatalogAlbumInFavorites(catalogId)`（未入库专辑用目录资源读状态）；
  - `setAlbumFavorite(catalogId, fav)` → PUT/DELETE ratings；
  - `rawWrite()`（写请求统一入口，body 至少 `'{}'`）；
  - 新增模型 `AlbumFavState`（已从 `musicbasic` 导出）；
  - **删除全部临时探测代码**（`probeRatings/probeFavorites/probeLibraryAlbums/probeFavorite*`、
    `EntryAbility` 里的探测调用也一并清掉）。
- `AlbumDetailPage`：
  - 新增 `isFavorite / favReady / favScale / favBusy` 状态；
  - `resolveFavoriteState()`：有资料库 id 就一次请求（`include=catalog&extend=inFavorites`）；
    否则按专辑名搜目录拿目录 id，再读目录资源的 `inFavorites`；
  - `toggleFavorite()`：**乐观切换心形** → 写 Apple；失败回滚；成功后等 7 秒
    `AppleLibrarySync.syncFavorites()` 重拉收藏列表 + `LibrarySignal.notifyChanged()`；
  - 心形按钮：**与艺人详情页完全同款**（52vp 圆形、`heart`/`heart_fill`、`#FF3B30`、
    spring 按压 0.9、共用 `buttonScale/buttonDy/buttonOpacity` 的入场动画），放在按钮排末尾；
  - 从专辑墙点进**已收藏**的专辑时，`openAlbumDetail` 会在收藏列表里反查并带上资料库 id（省一次搜索）。
- `AlbumsPage`：`onLibraryChanged()` 增加 `loadFavCache()` ⇒ 心形改动后专辑页顶部的收藏区**秒级跟随**（不再打网络）。

### B. 冷启动负载优化（每项都有真机日志为证）
| 项目 | 优化前 | 优化后 | 依据 |

| developer token 抓取 | 每次冷启动 2 请求 + **下载 index.js 3.3MB** | **0**（本地解 JWT 的 `exp`，>24h 才重抓） | `developer token 仍在有效期（1481 小时后过期），跳过抓取` |

- 新增 `AppleLibrarySync.syncSongs(onProgress?, force=false)`：自动路径走「快照判断」，**用户手动同步（顶栏/艺人页/搜索页/设置抽屉）传 force=true**，永远全量；

  新鲜期常量 `FULL_SYNC_MAX_AGE_MS = 6 小时`；
- 收藏新鲜度时间戳 `apple_fav_at_v1`（store `musichome_fav`），**页面与同步双向去重**（谁先成功谁写）；

- 歌单曲目同步无法用「总数对比」（Apple 的 library playlists 接口不返回 `trackCount`，库里恒为 0），

## 三十二、艺人详情页爱心不跟随 Apple 收藏（2026-09-26 晚，用户反馈）

用户反馈：在别的端把某位艺人收藏了，手机里**列表能显示**这位艺人（顶部的「收藏的艺人」横排 ✔），
但**点进艺人详情页后爱心是空的**（其它已收藏艺人是红色）。

### 根因
- 艺人页顶部横排的数据 = **本地收藏表 ∪ Apple 收藏名单**（合并显示 ✔）；
- 而艺人**详情页**的爱心只读本地收藏表 `MusicDbApi.isFavoriteArtist()` ⇒
  Apple 侧收藏、本地表里没有的艺人 ⇒ 爱心是空的 ✗。

### 先验证「艺人收藏能不能写回 Apple」（真机实测，目标选了未收藏的艺人，结束已复原）
| 调用 | 结果 |
|---|---|
| `POST /v1/me/favorites?ids[artists]={目录id}`（body `{}`） | **202** → 约 6 秒后 `inFavorites=true` ✔ |
| `DELETE /v1/me/favorites?ids[artists]={目录id}` | **204** → 约 6 秒后恢复 `false` ✔ |
| `GET /v1/me/library/artists/{r.xxx}?include=catalog&extend=inFavorites` | 一次拿到资料库 id + 目录 id + `inFavorites` ✔ |
（**注意与专辑不同**：专辑的收藏状态必须走 `PUT/DELETE /v1/me/ratings/albums/{id}`，
`POST /me/favorites` 对专辑无效；艺人反而只能用 favorites。）

### 实现
- `AppleApi` 新增：
  - `getArtistFavState(name)`：扫资料库艺人列表（带 `include=catalog&extend=inFavorites`，通常 1 页）⇒
    返回 `ArtistFavState{libraryId, catalogId, inFavorites, found}`；
  - `searchArtistIdByName(name)` + `getCatalogArtistInFavorites(cid)`：给**不在资料库里**的目录艺人兜底；
  - `setArtistFavorite(catalogId, fav)`：POST/DELETE `/v1/me/favorites?ids[artists]=…`；
  - 模型 `ArtistFavState`（已从 `musicbasic` 导出）；
- `MusicDbApi.setFavoriteArtist(name, favorite)`：新增**直接设值**接口（原来只有取反的 toggle，
  心形要「同时写 Apple」就必须知道确定值）；
- `ArtistDetailPage`：
  - 进入页面**同步**定状态：本地收藏表 ∪ **本地缓存的 Apple 收藏名单**（`apple_fav_artists_v1`，零请求、首帧即红）；
  - 再联网校准（`getArtistFavState`，顺带记下目录艺人 id）；
  - 点心形：**本地表 + Apple 一起写**（乐观更新，失败不管）；目录 id 还没拿到就现搜；
    写完后 7 秒 `syncFavorites(true)` 重拉收藏缓存 + 广播信号 ⇒ 列表与 Apple 保持一致。
- 真机证据：`APPLEART D'Angelo found=true lib=r.WKTGhxk catalog=640286 inFavorites=true`
  （探针，验证后已删）—— 能正确拿到目录 id 并读到 Apple 的收藏状态。


## 三十三、浅色模式：主页面背景流光改成「白 + 浅蓝」（2026-09-26 晚，用户要求）

用户要求：浅色模式下主页面的背景流光**更亮、删掉黑色**，只留**白色与浅蓝**。

### 改动（`products/default/src/main/ets/pages/Index.ets`）
1. 流光配色从写死的 `['#317AF7', '#8A8E96']`（蓝 + 灰 —— 浅色模式下那个灰就是"黑"的来源）
   改为按外观模式取（新增 `flowColors()`）：
   - **浅色**：`['#FFFFFF', '#4E9BFF']`（白 + 浅蓝）
   - **深色**：`['#317AF7', '#8A8E96']`（原配色，不变）
2. 新增 `refreshTheme()`：从 `AbilityContext.config.colorMode` 读**当前实际生效**的深浅色

- 灰 → 浅灰蓝（`#9CC6FF`）：亮了些但不够蓝，因为 shader 会把颜色洗淡；
- 灰蓝 → **清亮的白+浅蓝**（`#4E9BFF`）✔ 即最终值。
- 验证方法（**不动用户设置**）：临时在 `aboutToAppear` 里 `abilityCtx.setColorMode(COLOR_MODE_LIGHT)`
  + `flowColors()` 强制走浅色那套 → 截图确认 → **两处临时代码已删**，用户保存的外观模式（深色）保持原样。


## 三十四、浅色流光二次调优：补上 `colorTarget`（2026-09-26 晚，用户反馈）

用户反馈：深色那套现在合适 ✔，**浅色仍然颜色太深**。

### 关键发现：HDS 的 UVFlowLightColorParam 有 **两个**色组
`@hms.hds.hdsBaseComponent` 的接口定义：

```ts
interface UVFlowLightColorParam {
  colorSource: Array<ResourceColor>;          // 源色（我们之前只给了这个）
  colorTarget?: Array<ResourceColor>;         // 目标色（可选）
}
```

只给 `colorSource` 时，流光会朝**默认目标色**过渡 —— 浅色下整体就发灰发暗（用户说的"颜色太深"）。
把两套色都自己给（白 ↔ 浅蓝 互相流动），流光里就只剩我们自己指定的颜色。

### 最终配方（`Index.ets`，按模式分两段渲染）
| 模式 | 配置 |
|---|---|
| **浅色** | `colorSource: ['#FFFFFF', '#A8CDFF']`，`colorTarget: ['#A8CDFF', '#FFFFFF']`（白 ↔ 浅蓝） |
| **深色** | `colorSource: ['#317AF7', '#8A8E96']`（**不带 colorTarget**，保持用户认可的原观感不变） |

说明：深色**故意不补 colorTarget** —— 加了会改变深色观感，而用户明确说深色现在合适；这是"两套色互不影响"的做法。


## 三十五、浅色流光三次调优：量化定位 + 白纱压灰（2026-09-26 晚）

用户反馈二连："浅色模式之下还是太暗了，**能够明显地看出有黑色**"。于是改用**像素亮度测量**定位，不再靠肉眼。

### 量化结论
在固定背景空白区（标题下右侧 / 收藏行与"流行"之间的空隙 / 最右侧页边）测亮度中位数：

| 版本 | P1 | P2 | P3 | 说明 |
|---|---|---|---|---|
| 最初 `['#317AF7','#8A8E96']` | ~0.35 | ~0.27 | ~0.30 | 浅色下就是灰黑 |
| `['#FFFFFF','#4E9BFF']` | 0.42 | 0.36 | 0.40 | 只换色，几乎没用 |
| **全白配色**（source=target=`#FFFFFF`） | 0.54 | 0.51 | 0.54 | **铁证：与配色无关** |
| 全白 + 底下垫纯白底座 | 0.71 | 0.57 | 0.60 | 白底座能提亮一档 |
| 白+浅蓝 + 白底座 + **70% 白纱** ✔ | **0.89** | **0.83** | **0.86** | 最终采用 |

⇒ **UV 流光 shader 自身带一层灰**：即使把源色与目标色都设成纯白，背景也只有 0.52 亮度。
所以浅色模式下光调配色永远救不回来，必须**在其上再盖一层半透明白纱**。

### 最终实现（`Index.ets`，浅色三段式；深色完全不动）
```
浅色：① 纯白底座（Column, Color.White）
      ② UV 流光（colorSource ['#FFFFFF','#A8CDFF'] + colorTarget ['#A8CDFF','#FFFFFF']）
      ③ 白纱 Column('#B3FFFFFF')  ← 70% 白，压掉 shader 自带的灰
深色：UV 流光 colorSource ['#317AF7','#8A8E96']（不垫白底、不盖白纱，观感与用户认可的版本一致）
```
白纱的参数含义：越不透明越亮、流光越淡（70% 下流光约 ±2% 对比度，呈"很淡的蓝白流动"）。

### 测量方法（可复用）
`/tmp/lum2.py`：取三块确定没有内容的背景区，算亮度的 min/中位/均值，
既可给当次截图定位，也能把历史截图一起量做横向对比 —— 比"看截图感觉"可靠得多。
