# 播放详情页与歌词 —— 修复与优化记录（2026-10-17）

本轮针对用户反馈的三件事：
1. **歌词经常不高亮**：「播放到前一段时间时歌词不高亮，过了某个时间之后才正常」；
2. **重新优化整体播放逻辑的代码**；
3. **播放页面美观度对齐 Apple Music**。

---

## 一、开局状态：源码被写坏

`features/player/src/main/ets/view/AppleLyricsView.ets` 变成了 **2,097,438 字节 / 110,822 行**
的垃圾内容——每 76 个字符一个循环：

```
  private markUserScroll(): void {
    this.lastTouchAt = Date.now();
  }
<原文件的第 N 个字符>  private markUserScroll(): void { ... }
```

这是「逐字符遍历 + 每字符追加一整段替换文本」的脚本跑飞的结果（原文件的字符被
**逐字插入**在重复块之间）。因为结构完全规则，可以无损还原：

```python
s = open(fn, encoding='utf-8').read()
BLOCK_LEN = 75            # 重复块长度，实测 diff = 76 = 块 + 1 个原始字符
text = "".join(s[BLOCK_LEN::BLOCK_LEN + 1])   # 取每 76 字符的最后一个
```

还原结果：27,486 字符、874 行、括号平衡（`{`/`}` 各 173 个）—— **与真机上跑的那份
代码一致**，因此可以据此定位 bug，而不是盲改。

> 教训：改 ArkTS 文件**不要用命令行脚本做跨行正则替换/循环拼接**，一律用
> read / edit / write 工具做字面替换；脚本改文件必须「先写临时文件 + 校验括号与关键字
> + 再覆盖」。

## 二、歌词不高亮的真正根因（两个，叠加）

### 根因 A：`ForEach` 的 key 不变 → 子组件一直持有**旧对象**，`@Trace` 更新全部丢掉

旧实现在 `rebuild()` 里**每次都新建** `LineVisual` 对象：

```ets
const visuals: LineVisual[] = [];
for (...) { const vis = new LineVisual(); ... visuals.push(vis); }
this.visuals = visuals;
```

而列表是：

```ets
ForEach(this.lyric.lines, (line, idx) => {
  ListItem() { LyricLineItem({ visual: this.visuals[idx], ... }) }
}, (line, idx) => idx + '_' + line.key)     // ← key 只和行号/行 key 有关
```

`ForEach` 的 key 没变就**不会重建子项**，`@Param visual` 也不会被替换成新对象。
而 `rebuild()` 至少会被调用两次（`aboutToAppear` 一次按兜底宽度 320vp，
`onAreaChange` 拿到真实宽度再一次），于是屏幕上渲染的是**第一代对象**，
后面所有 `@Trace` 写入（逐字 alpha、空间渐隐）都写进了**第二代对象** ——
屏幕上那份永远停在初始值（灰字 0.32、fade=1）。

真机截图证据（修复前）：当前行区域峰值亮度 159（≈ 0.32 灰字），
而"该亮"的那一行本该是 255。修复后同一位置的峰值 = **255**。

**修法**（两处一起改，缺一不可）：
1. 把「换歌词」和「改排版」拆成两条路径：
   - `rebuildStructure()`：只在**歌词对象变化**（换歌/首次就绪）时调用，重建对象；
   - `relayout()`：宽度/字号/译文开关变化时只重算行高与渐隐，**对象不换**
     （词的切分本来就只跟文本有关，与宽度无关 —— 顺带省掉一次全量 token 重建）。
2. `ForEach` 的 key 里带上**结构代数** `gen`（只有换歌词时 +1），
   这样换歌时子项一定会重建，拿到新对象。

### 根因 B：时间源会漂移（旧实现在注释里已经量到「领先 15.6 秒」）

旧实现只有一条时间来源：`MusicAppState.progress`（AVPlayer `timeUpdate`，约 1s 一次），
再用「锚点 + 墙钟插值」补到毫秒。两个前提都不成立：

- `MediaService` 在 seek 之后会把 `isCurrent` 置 false 冻结进度（等 `seekDone`），
  那个回调偶发丢失时进度会冻住一段；歌的开头恰好是 seek/恢复最密集的地方；
- 「锚点 + 墙钟」只在播放位置与墙钟严格同步时成立，一旦有一拍没对上，
  插值就跑到真实播放头前面，而且**误差不收敛**。

歌词是**绝对时间轴**（每行 `begin` 都是相对整首歌的毫秒数），错 3 秒就落到别的行上；
歌的开头句子间隔只有 2~3 秒，于是「前半段完全不亮」，后半程句子间隔大就看不出来。

**修法**：新增 `LyricPlayhead`，**主源直接读 AVPlayer 的播放头**：

```ets
// MediaService
public playheadMs(): number {          // 一次属性读取，无异步、无额外开销
  const player = this.avPlayer;
  if (!player) return -1;
  const t = player.currentTime;
  return (!Number.isFinite(t) || t < 0) ? -1 : t;
}
```

`LyricPlayhead` 每 100ms 采样一次：采样值变了就以它为准确位置（误差 0）；
同一个值连续读到（底层属性粒度粗）才用墙钟补齐，**且补齐上限 2.5s**；
播放器未就绪（`< 0`）才退回 `state.progress` 锚点。所以「越播越偏」这一类问题
结构上不可能再出现。

## 三、播放逻辑的其它优化

| 位置 | 改动 | 收益 |
|---|---|---|
| `LyricsComponent` | 两份 `@Monitor('state.selectIndex','state.playQueueIds')` 合成一个 `reloadLyrics()` | 切歌时少走一次 rawfile 读取 + 一次多余的状态竞争 |
| `LyricsComponent` | 删掉死字段 `intervalId` / `pageShowTime` / `progress` / `progressText` 与根节点的空 `onClick` | 少一遍无意义的属性写入 |
| `AppleLyricsView` | 心跳只在**歌词页可见**时跑（`active` 由宿主按歌词页进度传入） | 封面页期间零逐字动画/滚动开销 |
| `AppleLyricsView` | 每次心跳只做一次二分 + 一次行比对；行没变、字没变直接返回 | UI 线程 100ms 一次、每次几微秒 |
| `AppleLyricsView` | 空间渐隐只在**换行**时重算（带 320ms 过渡），不是每帧 | 一屏几十个 `@Trace` 写入降到每秒一次 |
| `AppleLyricsView` | 逐字动画交给 `animateTo`（渲染线程插值） | 60fps 但 UI 线程不被每帧唤醒 |
| `AppleLyricsView` | 诊断日志默认关闭（`LYRIC_TRACE=false`），且只保留「换行」一行 | hilog IO 从「每次换行 2 长行 + 数组拼接」降到 0 |
| `MediaService` | 播放头对外暴露 `playheadMs()` | 歌词/进度这类毫秒级 UI 不再依赖 1s 事件 |

## 四、界面：向 Apple Music 对齐

### 歌词页

- **已唱过的字纯白、没唱到的压暗**：非当前行 0.36、当前行未唱部分 0.55
  （官方录屏量到 0.30，但那种背景更暗；我们背景是糊化封面的中浅色，
  0.30 压上去发灰发泥，抬到 0.36 才既有层次又读得清）；
- **当前行中心钉在屏幕高度 25%**（整首歌不动，列表在下面滚），
  `contentStartOffset` + `ScrollAlign.START` 实现；
- **歌词从「顶栏 + 小封面」下面开始排**：以前从 y=0 铺到 y=0，第一句会直接压在
  左上角封面/歌名上（截图里「时间等不了人」和「方大同」叠在一起）；
- 上下缘用官方 `linearGradientBlur` 做渐变模糊（钉在屏幕上，不随列表滚）；
- **底部新增紧凑播控**（上一首 / 播放暂停 / 下一首）：Apple Music 进歌词页后
  底部仍保留一行小播控，以前什么都没有，想暂停只能滑回封面页；
- **点左上角小封面/歌名 = 回播放页**（Apple Music 就是没有收起箭头）；
  同时修掉「收起箭头在歌词页里还显示着，但整层关掉了命中，看得见点不动」。

### 封面页

- **左下角新增「歌词」入口**（`sys.symbol.lyrics_square`，与 Apple 播放页同位置）：
  以前进歌词页只有「横向滑动」一条路，没有任何提示；
- 进度条视觉改细（轨道 6→4vp、圆点 18→16vp），命中区仍是 32vp 高
  （用户反馈过「点不了」，所以只改视觉不改热区）。

## 五、真机验证（无线调试 192.168.0.101:8710）

自检方式：临时在 `Index` 里加一段 demo（自动播一首带歌词的歌 + 程序化打开播放页），
`PhonePlaybackPage` 里定时切到歌词页，`MediaService.onPrepared()` 里 `setVolume(0)`
静音，然后按时间点连拍截图。**验证完这段临时代码已全部删除**（`TEMP-LYRIC-DEMO`）。

截图亮度测量（脚本 `tools/apple-music/measure-lyric-rows.py`，取每行笔画 99.5 分位亮度）：

| 版本 | 当前行（钉在 25% 处）峰值亮度 | 结论 |
|---|---|---|
| 修复前 | **159**（≈ 0.32 灰字） | 整屏都是灰字，没有高亮 |
| 修复后 | **255**（纯白） | 当前行正常高亮，且从歌曲**第 2 句**起就正确 |

补充验证：歌曲前段（L1/L2，1.4s / 4.6s 起）截图同样正确高亮 →
「前一段时间不高亮」的现象消失。

其它确认：`hilog` 无歌词相关错误（只有 HDS 主题缺失 + Navigation 参数序列化等既有噪声）。

## 六、踩坑清单（本轮新增）

1. **`ForEach` key 不变 ⇒ 子组件持有旧 `@Param` 对象引用**，`@ObservedV2`/`@Trace`
   的更新全部写进了孤儿对象 —— 这是本次「歌词不高亮」的元凶。
   凡是「重建对象后又按 index 做 key」的列表都有这个坑。
2. **`avPlayer.volume` 属性不存在**（编译报 10505001），静音要用 `setVolume(0)`。
3. 构建报 `ENOENT ... intermediates/default/temp`：
   该目录是 **指向 `/tmp/hv-temp` 的符号链接**，目标被清掉后 `mkdir -p` 也会失败，
   需要先 `mkdir -p /tmp/hv-temp`。
4. 升级 `@Monitor` 的使用：**同一个事件不要挂两份**（切歌时两条加载链各跑一遍）。
5. 源码被脚本写坏后**先做结构化分析**（找周期性），规则重复就能无损还原；
   直接重写会把上一轮辛苦调出来的数值（行高、渐隐、锚点）全部丢掉。
