## 一、这一版按「官方歌词页」的六个特征逐项重构

| 官方观感 | 旧实现 | 现在 |
|---|---|---|
| 远处那几句**真的糊掉** | 只有 opacity + scale，边缘依旧锐利 | 每行带自己的 `.blur()`：0 / 3.4 / 7 / 10.5 / 13.vp 逐级；外层再叠 `linearGradientBlur(20px)` 做上下缘更强 |
| 当前行**纯白 + 柔光** | 纯白、无光 | 当前行加「整行副本 + 整层 `.blur(7)`」作辉光层（不用 `textShadow`，见下方坑）；辉光只出现在已唱到的字上 |
| 只有当前句下面有**译文** | 每行都挂译文（压到 0.18），整页碎字 | 译文固定高度占位，可见度 0.72 / 0.22 / 0 跟随活跃行 |
| 背景是封面**大幅模糊且在流动** | 宿主一张静止模糊图 + 0.46 黑纱 | 歌词区内叠一张小尺寸重度模糊封面（缓慢 scale/translate）+ 会呼吸的暖光 + 暗纱（0.24） |
| 换行时整列**滑过去** | fade/scale 直接赋值，瞬间跳变 | fade / scale / blur / 译文统一 300ms 过渡；滚动仍是 `curves.springMotion(0.34, 0.84)` |
| 定位**永远钉在锚点** | 已有（垫片 + `getItemRect` + settle 校验） | 保留并沿用（这是唯一不累积误差的做法）；文字区边距改由组件内部施加，背景铺满整宽 |

## 二、关键取舍（为什么这么做）

1. **不用 `textShadow` 做字发光**：阴影按 Text **节点边界**裁剪，一行拆成十几个 Text
   后最边上那个字会在自己节点被切出一条笔直的竖向分界线（本项目实测踩过）。
   改成「整行副本 + 整层 blur」：副本与正文同结构（同 token / 同宽度），不会错位、不会切边。
2. **不用真实字号分级做「非活跃行变小」**：改字号会改折行数与行高 → 滚动定位全乱。
   继续用 `scale`（渲染变换，不参与布局），梯度 1.0 / 0.80 / 0.72 / 0.66 / 0.62。
3. **逐字填充仍是 33ms 按播放头直算**（`driveGlyphs`），不走动画框架插值 ——
   这条是前两版实测出来的（100ms 心跳→字一个个蹦；`keyframeAnimateTo`→整行瞬间全白；
   定时器 + `animateTo`→只有第一个字动）。
4. **背景图小尺寸渲染 + scale 放大**：模糊按渲染尺寸的像素算，0.62 倍图再放大 2.6 倍，
   等效大半径模糊但像素成本低一个量级。
5. **译文高度固定**（一行 + 省略号）：让行高稳定，滚动定位不被译文长短影响。

## 四、用到的鸿蒙官方能力

- `List` + `ListScroller.scrollTo` + **`getItemRect`**（真实矩形定位，官方 API）
- `curves.springMotion`（官方弹簧曲线，替代手写贝塞尔）
- `animateTo`（官方显式动画，属性由渲染线程插值）
- `linearGradientBlur`（官方渐变模糊，上下缘景深）
- 组件级 `.blur()`（官方高斯模糊，逐行景深）
- `radialGradient` / `linearGradient`（背景暖光与暗角）
- `@ObservedV2 / @Trace / @ComponentV2 / @Param / @Monitor / @Local`（V2 状态，属性级最小刷新）
- `SymbolGlyph`（头部/播控图标，沿用既有实现，未改）

> 没有用 `uiMaterial` 沉浸光感：HarmonyOS 7 起它只在「弹窗类 / Navigation 标题栏 / 底部 TabBar」
> 区域生效，歌词区不在白名单（已实测三次），用了也不渲染。

## 五、已知限制 / 下一轮可做

1. **头部与官方仍有差距**：官方小封面 80×80、右侧 ⭐/••• 两颗 37pt 玻璃圆钮；
   本项目是 44vp 小封面 + 歌名 + 「译」按钮。这部分属于宿主头部布局，
   本轮按「只动歌词页」的约束没有改。
2. **底部控制区**：官方歌词页与播放页共用完整控制区（进度/音量/三图标）；
   本项目歌词页只有一排紧凑播控（底部栏已冻结）。同样未动。
3. **行距**：因为用 scale 而不是真字号，非活跃行的行距比官方略大（官方字小、行距也小）。
   若用户要求「更紧凑」，下一轮可以在行上按距离加 `translate` 做堆叠收紧。
4. **性能观察点**：一屏约 8~12 行，其中 |距离| ≤ 4 的行才有 blur；
   若真机出现发热/掉帧，优先把 `BLUR_BY_DISTANCE` 整体乘 0.6，或把 `EDGE_BLUR_PX` 降到 14。

## 九、第三轮：按第二轮实测反馈修正（2026-10-30 23:05）

| 反馈 | 根因 | 改法 |
|---|---|---|
| 背景没有流动 | 只有一层官方 UV 流光，`FLOW_ALPHA 0.62` 又被暗纱 0.24 + 宿主黑纱 0.28 压掉，肉眼几乎看不出在动 | ① **加两团渐变色块光斑**（冷蓝 / 暖橙，520vp、`blur(46)`），11s 周期交错漂移 —— 不依赖 shader，一定看得见在流；② 官方流光 `FLOW_ALPHA 0.62→0.78`、周期 `12000→7000ms`；③ 暗纱 `0.24→0.10`、宿主 `LYRIC_SCRIM_ALPHA 0.28→0.20` |

## 十、第四轮：高光波形 + 末尾泛光 + 滚动时机（2026-10-30 23:2x）

| 反馈 | 改法 |
|---|---|
| 跳动还是滞后 | `LEAD_MS 180 → 240`（行判定与逐字同一个时钟） |
| 「不该整个字跳，应该随着高光从左到右的曲线跳」 | **废弃 popSoft（整字弹一下）**。位移/缩放改由 `sin(π × fill)` 每帧驱动：高光扫到字中间时抬到最高（`-1.05×w vp`），扫完自然落回 0。一行的时间窗首尾相接 ⇒ 整行是一道**连续的波**从右往左流过，而不是每字各弹一下。另在裁剪边外侧加一道 6vp 的白色渐隐，把「高光前沿」从硬边变成柔边 |

| 第二行到位太晚 | 滚动时机从「下一行开始才滚」改成**「当前行唱完就滚」**（`SCROLL_LEAD_MS = 100`）；时长 `380→300ms`，damping `0.72→0.92`（几乎不回过冲，观感更干净） |
| 动画不好看 | 滚动弹簧改为高阻尼（无晃动）；景深 scale 弹簧 `0.68→0.86`；只有字上的波形保留弹性 |

## 十一、第六轮：全粗体 + 暂停/续播/点击 seek 的稳定性（2026-10-30 23:5x）

### 1. 全粗体

未播放 / 已播放 / 正在播放**统一 Bold**（原来非活跃行是 Normal）。
顺带一个结构性好处：行高估算是按 Bold 量的，渲染也用 Bold 之后「估算行高 ≡ 实际行高」严格成立，
所以滚动目标（纯加法）在任何时刻都精确 —— 这也解释了之前偶发的「位置差一点」：
非活跃行用 Normal 时会少折一行，那一行的高度就比估算少 44vp。

### 2. 断断续续暂停时的三个坑（都已修）

| 现象 | 根因 | 修法 |
|---|---|---|
| 暂停时画面自己换行 / 乱跳 | `LyricPlayhead` 的墙钟外推上限是 **2.5s**：播放头不更新（暂停、缓冲）时位置会被虚推到 2.5 秒之后，跨过一行 → 自己换行，再被真实播放头拉回 | 外推上限 **2500 → 400ms**（小于最短句子间隔，跨不过一行） |
| 暂停期间轻微抖动也被当成 seek | `jump` 判定用 `|Δ| > 1500` 且不分播放态；跳变后又把 `scrollAnchorIdx` 清成 -1，于是**下一拍必然再重滚** | 阈值 `1200`；跳变只重算整列 + 标脏一次（做一次重对齐），不再逐拍重滚 |
| 暂停中任何状态变化都会触发滚动 | 滚动分支只看 `!browsing` | 新增 `allowScroll = playing OR jumped OR force OR wasBrowsing` —— **暂停时画面必须静止**（用户暂停就是为了看这一句） |

### 3. 点击某一行立刻对齐

`jumpTo()` 原来只把 seek 丢给播放器，要等播放头/seek 完成才滚动 —— 中间几百毫秒画面停在旧位置，
看起来像「点了没反应 / 位子乱跳」。现在点击的同一帧就 `applyActive(idx)` + 滚到该行（用回位曲线）。

新增/变更参数：`LyricPlayhead.MAX_EXTRAPOLATE_MS`(400) / `jump` 阈值(1200) / `allowScroll` 条件。

## 十二、第七轮：折行恒定 + 换行弹性（2026-10-30 23:5x）

### 1. 「正在播放时字体变大 / 一行变两行」——根因是三层渲染宽度不一致

一句话：**活跃行比非活跃行宽了 Σ1.5vp**。

| 层 | 以前的排版宽 | 结果 |
|---|---|---|
| 非活跃（`dimLayer`） | `Text` **自然宽度** | 总宽 = 真实文字宽 |
| 活跃（`activeLayer`） | `Stack.width(widthVp)`，`widthVp = measureText + 1.5vp` | 总宽 = 真实宽 + 1.5 × 段数 |

一行常被切成 15~25 段 → 活跃行凭空宽出 **22~37vp**。临界行（刚好排满一行）于是：
非活跃态一行排下、切到活跃态多折一行 → 视觉上「字被放大 + 行数变了 + 后面所有行被推下去」。
而 `rowCount`（行高估算）用的是 `measureText(整行字符串)`（等价于"无额外宽度"）→ 估 1 行、
实际渲染 2 行 → 行高不足 → 溢出压到下一行，切换那一刻更难看。

顺带 `SCALE_ACTIVE=1.0` vs `SCALE_NEAR=0.80` 的 25% 落差，以及辉光层 blur（9vp）的膨胀观感，
共同造成"字体被放大"。

**修法（三条一起上，少一条都还会抖）**

1. **宽度公式统一**：`tokenWidthVp = measureText(段) × px2vp + 0.4`（余量 1.5 → 0.4，仅防白字右缘被裁），
   取整到 0.1vp。
2. **三层都按 `widthVp` 固定宽渲染**：`dimLayer` 的 `Text` 与 `activeLayer` 的灰字 `Text` 都加
   `.width(widthVp).maxLines(1).textOverflow(Clip)` —— 三层的折行点从此**必然相同**。
3. **行高按逐段累加模拟 Flex 换行**：新增 `measureLineRows()`，`relayout` 里用它替代
   `LyricLineLayout.rowCount()`（后者测整行字符串），并顺手把**所有行**的段宽一次量好
   （原来只有活跃行才量）。附带收益：原来 `rowCount` 用 `widthOf(累加串)` 是 O(n²) 次 measureText，
   现在是 O(n) 次，首屏排版更快。
4. 缩放档位收窄：`1.0 / 0.94 / 0.90 / 0.87 / 0.85`（原 `1.0 / 0.80 / 0.72 / 0.66 / 0.62`）。
   层次改由 alpha + 真模糊承担（这才是 Apple 的做法），尺寸只做一点点暗示。

> scale 本身是纯渲染变换、不影响折行，所以"跳变"主要来自宽度不一致；把宽度修齐后
> 缩放的落差再怎么调都不会改变行数了。

### 2. 「换行动画依旧是线性的」——有一层确实没用弹簧

`applyDepth()` 里本来是两段动画：

```
透明度 / 模糊  →  animateTo({ duration: 340, curve: Curve.EaseOut })      ← 硬
尺寸(scale)    →  animateTo({ duration: 620, curve: curves.springMotion() })  ← 弹
```

用户感知的"线性"就是第一行：`Curve.EaseOut` 是匀速收尾的缓动，改行时整列亮度一起来就发硬。
现在两层都用**鸿蒙官方弹性曲线** `curves.springMotion(response, dampingFraction)`：

| 层 | duration | response | damping | 观感 |
|---|---|---|---|---|
| 透明度 / 模糊 | 520ms | 0.44 | 0.74 | 柔和地亮起，略微过冲一点点 |
| 尺寸 scale | 640ms | 0.56 | 0.62 | 整列像被按住后松开，滑过去 |

阻尼取值要点：透明度那一层低于 0.7 会「先亮过头再退回」，看起来像闪，所以 0.74 是下限。

滚动另作处理：`SCROLL_RESPONSE` 0.28 → 0.36（更缓），**阻尼保持 0.95**（不过冲）——
用户明确不喜欢「跳过头再弹回来」，滚动弹性不做，弹性只放在景深/亮度这一层。

### 3. 本轮参数表（新增 / 变更）

| 常量 | 旧 | 新 |
|---|---|---|
| token 宽余量 | +1.5vp | +0.4vp |
| `SCALE_NEAR/FAR/FARTHEST/AWAY` | 0.80/0.72/0.66/0.62 | 0.94/0.90/0.87/0.85 |
| `DEPTH_FADE_MS / RESPONSE / DAMPING` | 340(共用) / 0.40 / 0.86 | 520 / 0.44 / 0.74 |
| `DEPTH_SCALE_MS / RESPONSE / DAMPING` | 620 / 0.40 / 0.86 | 640 / 0.56 / 0.62 |
| `SCROLL_RESPONSE` | 0.28 | 0.36（阻尼仍 0.95） |

新增方法：`AppleLyricsView.tokenWidthVp()`、`AppleLyricsView.measureLineRows()`。
`LyricLineLayout.rowCount()` 保留（别处可能用），但歌词页不再调用它。

## 十三、第八轮：让每一次换行都真的滚到位（「越到后面越不灵」）

### 症状与误判

用户反馈：换行滚动不灵敏，有些对有些不对，**尤其越到后面出错概率越高**。

「越到后面越容易错」听着像累积误差，但**不是**。本轮先做了一次数值验证（按真实参数
`H=620 / anchor=0.455H / 行高 44+28`，60~200 行、行高随机 1~2 行），结论：

> 旧底部垫片 `H − anchor` 的行程**足够**让每一行（含最后一行）都落到锚点。
> 最大滚动量 = Σ行高，最后一行中心 = Σ行高 − h_last/2，恒小于它 —— 所以"末尾滚不到"这个假设不成立。

同时 `targetOffsetFor()` 的纯加法也有个容易看错的地方：
`lineCenters` 是**不含顶部垫片**的累加值，而顶部垫片高 = anchor，于是
`视口 y = (anchor + cᵢ) − cᵢ = anchor` —— 少算 anchor 恰好抵消，恒等于锚点。也对。

所以真正的问题是**滚动请求被静默丢弃 / 被误判**，一共三处：

### 1. 漏滚 → 永久丢（最严重）

```ts
if (anchorIdx !== this.scrollAnchorIdx || force) {
  this.scrollAnchorIdx = anchorIdx;   // ← 先标记「这一行已经滚过了」
  this.scrollTo(anchorIdx, ...);      // ← 内部可能 return（节流/DOM 未就绪）
}
```

而 `scrollTo` 里有一句时间节流：`now − lastScrollAt < 260×0.7 ≈ 182ms` 就 return。
于是一旦被挡：锚点标记已经是新值 → 下一拍 `anchorIdx === scrollAnchorIdx` → **这一行永远不会再补**。
歌越到后面句子越密、滚动请求越频繁，落进 182ms 窗口的概率越高 → "越往后越不灵"。

**修法**：`scrollTo` 改为返回 `boolean`，**只有真的执行了才写 `scrollAnchorIdx`**；
被挡就保持旧值，下一拍（66ms 后）自动重试，直到成功。同时删掉时间节流
（绝对目标 + 弹簧，连续重定向本来就是平滑的，不需要"动画期间不许动"）。

### 2. 程序化滚动被当成「用户在滚」→ 自冻 4 秒

```ts
.onScrollStart(() => { if (Date.now() - this.lastScrollAt > 500) this.userScrollAt = Date.now(); })
```

自动滚动也会触发 `onScrollStart/Stop`，所以用"距上次下发滚动 < 500ms"来区分。
**但回位动画是 520ms**，结束时早已超过 500ms → 被判成用户滚动 → 跟随冻结 4 秒。
越到后面滚动越频繁，这个误判越容易命中。

**修法**：新增 `programmaticUntil = now + 动画时长 + 200ms`，窗口内的
`onScrollStart/Stop` 一律不算用户滚动。

### 3. 轻轻碰一下屏幕就冻结跟随

`.onTouch()` 以前不看事件类型：手指 **Down** 就写 `userScrollAt` →
`isBrowsing()` 为 true → 4 秒内不跟随。点行、误触都算。

**修法**：只有 `TouchType.Move`（真的在拖）才算用户在浏览上下文。
`lastTouchAt`（900ms 判定）仍然无条件更新，所以"按着看"依旧生效。

### 4. 顺带调整

| 参数 | 旧 | 新 | 原因 |
|---|---|---|---|
| `SCROLL_LEAD_MS` | 100 | 150 | 上一行最后一个字刚落音就启动，下一句开口时动画已走完 |
| `SCROLL_DURATION_MS` | 260 | 240 | 跟句子节奏更贴（阻尼 0.95 不变，仍不过冲） |
| 底部垫片 | `H − anchor` | `H − anchor + 12` | 只补像素取整余量（数值验证过原式够用） |

新增字段：`programmaticUntil`、`lastScrollY`。
新增日志：滚动未执行时打一条 `滚动未执行 #N，下一拍重试`（正常播放零日志），
下一轮若还有问题，可以直接抓 hilog 看是哪一拍被挡。

## 十四、第九轮：按实录视频做像素级对齐（2026-10-30 23:3x）

素材：用户实录 Apple Music 歌词页 `SVID_20261030_231819_1.mp4`（890×1920 / 31.96s / 60fps 源）。
换算：录屏 890px 宽 = 本机 387.7vp ⇒ **1px = 0.4356vp**（抽帧缩到 445 宽时 1px = 0.8712vp）。

### 测量方法（可复用）

1. `ffmpeg -vf fps=1/fps=30/fps=60,scale=445:-1` 抽帧；
2. 逐帧做**行投影**（`rowmax − 40% 分位`）找出每个文字带的 `y0 / 高度 / 峰值`；
3. 对指定带做**列投影**得到墨迹水平范围 → 折算字宽 → 字号（中文 em ≈ 字宽）；
4. 峰值对比「同一行右侧空白区」得到 alpha；
5. 用「20%→80% 上升距离」估模糊半径；
6. 跟踪同一带的 `y0` 随时间变化得到滚动曲线。

### 实测结果（屏 387.7×837vp）

| 项 | 实测值 | 本轮改动 |
|---|---|---|
| 行内行距 | **42.7vp**（49px） | `LINE_HEIGHT_VP` 44 → **42.5** |
| 段间「行顶到行顶」 | **74.9~76.7vp** | `PARA_GAP_VP` 28 → **32**（42.5+32=74.5） |
| 当前句**首行**中心 | 屏高 **25.5%**（213.5vp） | `ACTIVE_IN_AREA` 0.455 → **0.255** |
| 当前行字号 | em ≈ **35vp** | 不变（fontSize 35） |
| 其它行字号 | em ≈ 33~35vp，**与当前行几乎相同** | `SCALE_*` 全部 → **1.0** |
| 灰字 alpha（距离 1/2/3/4 行） | **0.23 / 0.19 / 0.14 / 0.11** | 新增 `DIM_ALPHA_BY_DISTANCE`，按距离分级 |
| 模糊半径（距离 1~4） | 约 **2~4vp**（边缘上升 5~7px，清晰标题基线 2px） | `BLUR_BY_DISTANCE` 3.4/7.0/10.5/13.0 → **2.4/4.0/5.2/6.4** |
| 换行滚动 | **133ms** 走完 **56.6vp**，S 形、无过冲 | `SCROLL_DURATION_MS` 240 → **150**；`springMotion` response 0.36 → **0.20**，damping 0.95 → **0.92** |
| 上一句变灰 | 换行后 3 帧（≈100ms）已降为灰 | 淡出 300 → **180ms** |
| 逐字高亮 | **字内从左到右填充**（非整字放大/上浮） | `POP_GAIN` 0.026 → **0**，`LIFT_BASE_VP` −1.05 → **0** |
| 下一字 | 开唱前 ~150ms 开始整体提亮（4 帧内 102→199） | 新增预热：`PREHEAT_MS` 220 / `PREHEAT_ALPHA` 0.55 |
| 背景 | 三块取样亮度 range 22~40（缓慢漂移） | 已有 blob 漂移，保持 |

滚动曲线逐帧（60fps，位移 px）：`0 / 1 / 4 / 8 / 13 / 23 / 36 / 55 / 64 / 65`
—— 前 5 帧只走 13px（8%），中间两帧冲 10→19px，最后两帧 9→1px 收住，是典型 S 形。

### 本轮纠正的三个此前错误认知

1. **「非活跃行字号约 0.68 倍」是错的**。实测当前行 5 个字墨迹 196px、灰行单字 36px /
   两字 72px，折算 em 分别是 ≈35vp 与 ≈33~35vp。Apple 的层次**不是靠字号**，
   而是靠「纯白 vs 灰 0.11~0.23」+「清晰 vs 真模糊」。所以之前用 `scale 0.85` 缩小非活跃行
   会让它看起来更小、更"远"，反而偏了；也会让用户觉得「切到当前行时字被放大」。
   → 现在 `SCALE_*` 全 1.0，**折行与行高永久恒定**。
2. **逐字高亮是「字内填充」，但没有任何整字缩放/位移**。连环 4 帧量同一行：
   墨迹 x 范围恒为 38..233、峰值恒 255、基线 ±1px。之前的 `pop 1.026` + `lift −1px`
   是照"活泼"加的，与官方不符，已归零。
   填充边界在字内有 **约 12px（10vp）的柔化过渡**（这是 Apple 的 `LineProgressGradientLayer`），
   我们目前是硬裁切 —— 见下方「未复刻项」。
3. **锚点是 25.5%，不是 45.5%**。之前按"中间靠下"定在 0.455，与官方差 ~170vp。
   注意官方是让**该句第一行**钉在 25.5%（多行句子往下长），所以 `lineCenters` 也从
   「行块中心」改成「行块顶部 + 半个行高」。

### 未复刻项（诚实记录）

- **填充边缘的 10vp 柔化**：ArkUI 的 `clip(true)` 是硬边，没有渐变遮罩原语
  （`mask()` 只吃几何形状）。可选项：在白层右缘叠一条 10vp 的「白→透明」渐变条，
  但宽度随 fill 连续变化时会出现接缝，暂不做。
- **流光/材质**：实录背景是专辑封面重度模糊 + 缓慢漂移（我们已有 blob 漂移）。
  视频里没看到额外的边缘流光层，所以没有加新的 shader。

## 十五、第十轮：逐字「上跳后停留」+ 到位速度与命中率（2026-10-30 23:5x）

### 1. 逐字效果：方向改过来了

用户指出：官方的逐字效果是「字被唱到时往上一跳，然后**停在上面**」，
不是"先升后落"，也不是"逐个放大"。

之前的实现是 `lift = LIFT_BASE_VP · w · sin(πp)` —— 正弦波：唱到字中间抬到最高、
唱完落回基线。方向确实反了。

现在的实现：

| 阶段 | lift（负值=向上） | 说明 |
|---|---|---|
| 未唱 | 0 | 在基线上 |
| 刚开唱的前 55% | **−3.4vp** | 过冲，做出"弹一下" |
| 后半 + 唱完之后 | **−2.2vp** | **停住**，不回基线 |

于是整行唱过的字都比没唱的高一截，从左往右一级一级跳上去 —— 台阶感。
上一句变灰时 `applyActive` 会把 lift 归零，所以灰行是平的。

`JUMP_VP` / `JUMP_OVERSHOOT_VP` 放在常量区，改幅度只动这两个数。

> 诚实说明：我把你这段录屏里那一行（11.4s「我爱故我在」）5 个字逐个量了顶端 y，
> 四帧之间只在 ±1~2px（<1vp）内动，**测不出明显的上跳**。所以这一条是按你的
> 观察实现的（网页版可能比 iOS 版更收敛），幅度 2.2vp 是我给的默认值。

### 2. 渐变更细腻：smoothstep 取代幂函数

```ts
// 旧：f = Math.pow(t, 1.6)        ← 锚点附近有个"折角"，越近变化越快
// 新：f = t*t*(3-2*t)             ← smoothstep，两端斜率为 0
```

底部尾部同样改成两段 smoothstep 相乘（中段收 + 尾部归零），过渡不再有硬拐点。

### 3. 到位速度与命中率（三处）

**(a) 滚动启动点改成「按下一句开唱时刻反推」**

```ts
const byNext = nextStart - SCROLL_DURATION_MS - 40;   // 保证下一句开口前动画结束
const startAt = max(byNext, curEnd - SCROLL_LEAD_MS); // 但不早于上一句唱完
```
旧逻辑只认 `curEnd`（上一句唱完才启动）。遇到句间空隙很小的快歌，
新句已经开口了动画才刚开始 —— 这正是"到位太晚"。现在以 `nextStart` 为基准倒推，
空隙够大就晚点动（不破坏"高亮固定在锚点"），空隙小就紧跟 `curEnd` 立刻动。

**(b) 触摸冻结 900 → 420ms**
手指蹭一下屏幕就冻结跟随 0.9 秒，是"有时不滚"的主要体感来源。

**(c) 行高自检（每行一次，最多 3 次）**
用 `scroller.getItemRect(idx+1)` 拿 List 给的**真实矩形**，和纯加法目标比：
偏差 > 9vp 说明行高估算与真实渲染不一致（典型原因：首屏测量发生在字体就绪之前，
`measureText` 偏小 → 折行算少 → 后面所有行累积偏移），这时 `relayout()` 重排一次并
强制重滚。**不做每拍补滚**（那才是"跳多了又回去"）。

### 4. 参考的开源实现（供以后对照）

- [AMLL / applemusic-like-lyrics](https://github.com/amll-dev/applemusic-like-lyrics)：最完整的 Apple Music 风格歌词开源实现（Web 端，逐字用 CSS 变量驱动亮度/缩放）
- [flutter_lyric 的 appleMusic 预设](https://pub.dev/documentation/flutter_lyric/latest/flutter_lyric/LyricPresets/appleMusic-constant.html)：有现成的 Apple Music 参数集
- [Takpap/apple-music-lyrics](https://github.com/Takpap/apple-music-lyrics)：直接读 Apple Music 本地 TTML 缓存的 macOS 实现

它们的逐字效果多为「亮度 + 轻微缩放」，与用户观察到的「上跳后停留」并不一致，
所以本轮以用户观察为准，没有照搬。

## 十六、第十一轮：把「每拍写值」全部换成真动画（2026-10-30 23:5x）

用户四条反馈：到位速度还不够、别用行高自检、台阶感顿挫、能看到明显白灰边界。

其中「顿挫」和「白灰硬边」其实是同一个病根：**我一直在用 42~66ms 的心跳去逐帧写样式值**，
而不是让引擎自己跑动画。写值只有采样点，采样点之间就是"跳"；而且写值写出来的一定是硬边。

### 1. 到位速度：上一句唱完就滚，且只滚 130ms

| 参数 | 旧 | 新 |
|---|---|---|
| `SCROLL_LEAD_MS` | 150（提前 150ms 滚） | **0**（`curEnd` 一响就滚） |
| `SCROLL_DURATION_MS` | 150 | **130** |
| `CONDUCTOR_MS`（心跳） | 66 | **42** |

- 提前滚会把还在唱的白字行往上推（破坏"高光固定在锚点"），所以不能提前；
- 但也不能晚——现在**判定时刻 = 上一句结束时刻**，句间空隙整段用来跑那 130ms 动画；
- 心跳从 66 → 42ms：判定精度提高 36%，减少"该动的那一拍刚好错过，多等一拍"。

### 2. 行高自检已删除

`checkLayoutOnce()`、`layoutCheckedIdx`、`layoutFixCount`、`getItemRect` 全部移除。
滚动回到纯粹的「行高钉死 + 纯加法目标」，一行一跳，不做任何事后校正。

### 3. 台阶感：一个字只下一次动画

旧实现（顿挫的原因）：

```ts
const liftWant = p < 0.55 ? -3.4 : -2.2;   // 两档
if (Math.abs(tk.lift - liftWant) > 0.02) {
  tk.lift = liftWant;                       // 每拍直接写值
}
```

66ms 一拍、还经常错过采样点 → 看到的是"两下"。

新实现：每个字**只在自己开唱的那一刻**触发一次动画，之后不再碰它：

```ts
if (!tk.jumped) {
  tk.jumped = true;
  animateTo({ duration: 260, curve: curves.springMotion(0.26, 0.55) }, () => {
    tk.lift = -2.2;      // damping 0.55 → 曲线自己做过冲与落定
  });
}
```

字与字按演唱顺序依次触发，于是整行是一道**连续的波浪**往上抬。
上一句变灰时，先用同一族弹簧把 lift 动画回 0（220ms），再折叠成单层灰字——
不再"啪"地一下掉回基线。

### 4. 白灰边界：给"正在长白层"的那个字加一点模糊

填充是 `Stack.width(fill×w).clip(true)`，`clip` 是硬边，所以白灰交界是一条刀切线。

现在给白字层的裁剪容器加 `.blur(t.edgeBlur)`，**只在 fill ∈ (0,1) 时**为 1.15vp，
唱满立刻归零：

- 边界从"硬切"变成约 1vp 的过渡；
- 只有正在填充的那一个字有模糊，其余字完全清晰（不会让整行发虚）；
- 每行同一时刻最多一个字在填充，所以性能开销可忽略。

> 这是近似手段：ArkUI 没有 alpha 渐变遮罩（`mask()` 只吃几何形状），
> 官方的 `LineProgressGradientLayer` 是真正的 10vp 渐变带。若还需更柔，
> 把常量 `eb = 1.15` 调大到 1.8~2.2 即可（代价是白字略微发虚）。
