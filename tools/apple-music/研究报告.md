## 二、为什么绕不开 DRM（实测证据）

在真机上跑了三个实验：

**实验 1｜系统 DRM 清单（原生 DRM Kit）**
```
drm.getMediaKeySystems() → 只有 1 个：com.wiseplay.drm
com.widevine.alpha     = false
com.microsoft.playready= false
com.apple.fairplay     = false
com.wiseplay.drm       = true      ← 唯一
```

**实验 2｜浏览器内核 EME（ArkWeb）**
```
com.widevine.alpha      → NotSupportedError
com.microsoft.playready → NotSupportedError
org.w3.clearkey         → OK
com.wiseplay.drm        → OK
```

**实验 3｜真实打开 music.apple.com，hook 它的 DRM 请求**
```
REQ com.microsoft.playready → ERR
REQ com.widevine.alpha      → ERR
REQ org.w3.clearkey         → OK
REQ com.apple.fps           → ERR      ← FairPlay
```

**结论**：Apple Music 全曲是 FairPlay/Widevine 加密的，而鸿蒙设备三样都没有（只有中国标准 WisePlay）。这是**结构性缺失**（Widevine 授权依附 Google GMS 体系），升级系统不会改变。所以任何"在鸿蒙里播放 Apple Music 流"的方案，都必须自带 Widevine 解密——这就是那位 UP 主"攻克 DRM"的真实含义。

**资源开销参考**（同一台机器实测）：用 ArkWeb 包装 Apple Music 网页版时，主进程 158MB + 渲染进程 181MB ≈ **339MB**；纯本地播放器一般 100–150MB。

## 三、方案②：电脑下载 → 手机本地播放（本目录工具）

**原理**：把 Apple Music 的歌在电脑上下载成普通 m4a（解密后），手机只做本地播放 —— 手机端零 DRM 依赖。

**已验证的事实**：
- ✅ 不需要 Apple Developer 账号（省 688 元/年）：developer token 由工具自动从 music.apple.com 抓取（实测拿到 `iss: AMPWebPlay` 的 JWT，有效期约 70 天）
- ✅ 不需要自己找 Widevine 凭证（.wvd）：gamdl 内置了一份 L3 凭证
- ✅ 工具链跑通：gamdl 3.8.5 + pywidevine 1.9.0 + Python 3.14（本机）

**你只需要做**：拿到 `media-user-token` cookie → 跑脚本。步骤见 `README.md`。

**两种听法**（都已实现）：
- **离线**：`./am-dl.sh <链接>` 下载 → `./sync-to-phone.sh` 推到手机 → 你自己的播放器听
- **在线（家里）**：`python3 music-server.py` → 手机浏览器打开电脑地址，直接搜/播/下载（零依赖，实测首页 200 / API 正常 / 音频 Range 206）

**局限**：不是流媒体体验——要听新歌得回电脑同步一次。适合"歌单固定、离线听"。

## 四、方案①的音量问题（值得再试一次）

你说过卓易通里 Apple Music **能播但音量跟原生应用不一致**。能让它出声，就说明**容器内有 Widevine L3**——这条路其实只差音量体验。可以按顺序试：

1. **鸿蒙的单应用音量调节**（最可能有效）
   HarmonyOS 6.x 支持按应用单独调音量（PC 端 MateBook 6.1 已明确支持；手机端在
   `设置 → 声音和振动` 或控制中心长按音量条查看）。把**卓易通**这一路的音量单独拉满，
   看是否与原生应用对齐。
2. **容器内音量拉满**：在卓易通里播放时，用容器内的音量控制（或安卓侧音量面板）调到 100%，
   之后只用鸿蒙音量键控制——避免两套音量曲线叠加导致"总是偏小"。
3. **蓝牙耳机 / 音箱**：走 AVRCP 绝对音量，通常能绕开容器音频通路的增益差异，最省事地验证
   "是不是容器增益问题"。
4. **对比测试**：同一首歌分别用「华为音乐」和「卓易通里的 Apple Music」放，用手机的分贝 App
   （或手机自带的测噪）看差距是固定 dB 还是随机——固定偏差说明是增益曲线问题（可补偿），
   随机波动说明是音频通路不稳定（难搞）。

如果第 1、2 条能解决，那就是**零开发的最优解**，直接回去用卓易通即可。

## 五、方案③：自研鸿蒙客户端（如果你想要"手机原生体验"）

那位 UP 主做的就是这个。技术拆解（我逐项验证过的可行性）：

| 环节 | 怎么做 | 可行性 |
|---|---|---|
| 账号登录 | 用 ArkWeb 加载 music.apple.com 让用户登录，用 `WebCookieManager` 取 `media-user-token` | ✅ 标准能力 |
| Developer Token | HTTP 抓 music.apple.com 首页的 index.js，正则取 JWT | ✅ 已在本机验证成功 |
| 元数据/资料库 | 调 `amp-api.music.apple.com`（Bearer token + media-user-token cookie） | ✅ 现成 REST 接口 |
| 取播放资源 | web playback 接口拿 HLS 清单（含 PSSH 与 license URL） | ✅ |
| **Widevine 解密** | 内置 L3 凭证 → 生成 license challenge（RSA-SHA1 签名 + protobuf）→ 向 Apple license 服务器取 key → AES 解密 | ⚠️ **核心难点**，需把 pywidevine 的逻辑移植到 ArkTS/NDK（可用鸿蒙 Crypto Kit，或 NDK + OpenSSL） |
| 内容解密 | CENC/AES-CTR 解密 HLS 分片 | ✅ 算法明确 |
| 播放 | 解密后写本地 m4a → AVPlayer 播放（或组 fMP4 流式播） | ✅ |

**工作量估计**：核心解码链路约 3000+ 行 ArkTS/C++，业余时间 2–4 周。封装成"边下边播 + 缓存"后体验接近官方。

**风险**：违反 Apple Music 条款（可能封号）；Apple 改协议就得跟进维护；仅限个人自用，不能上架也不应传播。

## 六、我的建议顺序

1. **先试第四节 1、2 条**（10 分钟）：如果卓易通音量能对齐，直接用，零成本。
2. **同时把方案②跑起来**（拿到 cookie 后 5 分钟）：做你的离线曲库，配合你自己的播放器项目用。
3. **想要"原生手机端体验"再考虑方案③**——我可以做，但需要投入时间，且要接受封号风险。
